# EvoRoute: ローカルLLMのための進化的ルーティング最適化

## 概要

ローカル環境で動作する複数のLLMに対して、タスクごとに最適なモデルを自動選択するルーターを構築する。ルーティング戦略の改善には進化的探索を用い、精度・速度・メモリ効率のバランスを自動で最適化する。

APIベースのルーティング研究とは異なり、モデルのロード時間・メモリ制約・量子化レベルといったローカル環境固有のコストをルーティング判断に組み込む点が本プロジェクトの特徴である。

## 背景

### 課題

ローカルLLMの利用が拡大する中で、以下の問題がある。

- 単一モデルでは、すべてのタスクに対して精度と速度を両立できない
- 大きいモデルは高精度だが遅く、メモリを多く消費する
- 小さいモデルは高速だが、複雑なタスクでは精度が落ちる
- ローカル環境ではモデルの切り替え（ロード/アンロード）にコストがかかる

### 先行研究

| 研究 | 対象 | 手法 | 本プロジェクトとの違い |
|------|------|------|------------------------|
| RouteLLM (2024) | API (GPT-4 vs Mixtral等) | 学習型分類器 | APIコストのみ考慮。ロード時間・メモリ制約なし |
| FrugalGPT (2023) | API (GPT-4 vs GPT-3.5等) | カスケード＋学習 | API料金の最適化が目的。ローカル制約なし |
| Hybrid LLM (2024) | API | 品質予測による振り分け | 2モデル間の選択。ローカル固有コスト未考慮 |

既存研究の多くはAPI間のルーティングを扱い、コストはAPI料金やトークン数で定義される。ローカル環境ではモデルのロード/アンロード時間、VRAM/RAM上限、量子化による精度劣化など、異なるコスト構造が存在する。

## 目的

1. ローカルLLM間のタスクルーティングを実装し、固定モデル方式と比較する
2. ローカル環境固有のコスト（ロード時間、メモリ使用量、量子化レベル）をルーティング判断に組み込む
3. 進化的探索によるルーティング戦略の自動改善が、手動設計の戦略を上回るか検証する

## 設計

### アーキテクチャ

```
タスク入力
  │
  ▼
特徴量抽出 ─── タスク種別、入力長、キーワード、要求精度
  │
  ▼
ルーター ────── 特徴量 → モデル選択（戦略に基づく）
  │
  ├─→ 軽量モデル (1.5B, Q4)
  ├─→ 中型モデル (3.8B, Q8)
  └─→ 大型モデル (7B, Q4)
  │
  ▼
評価エンジン ── 正答率、実行時間、メモリ使用量、ロード時間
  │
  ▼
進化的探索 ─── 戦略の生成 → 評価 → 選択 → 変異 → 次世代
```

### ルーティング戦略の表現

進化的探索では、ルーティング戦略を以下のような条件木として表現する。

```python
# 戦略の例（探索対象）
strategy = {
    "rules": [
        {"if": "task_type == 'classification' and input_length < 200",
         "then": "small_model"},
        {"if": "task_type == 'reasoning'",
         "then": "large_model"},
        {"default": "medium_model"}
    ]
}
```

進化的探索は、このルール構造自体を変異・交叉・選択することで改善する。パラメータの最適化ではなく、ルーティングロジックの構造探索を行う。

### 評価関数

```
J = Accuracy - λ₁·NormalizedLatency - λ₂·NormalizedMemory - λ₃·LoadSwitchPenalty
```

- **Accuracy**: タスクごとの正答率（分類: F1、抽出: Exact Match、推論: 正答率）
- **NormalizedLatency**: 実行時間を最大値で正規化
- **NormalizedMemory**: ピークメモリ使用量を正規化
- **LoadSwitchPenalty**: モデル切り替え回数に応じたペナルティ（ローカル固有）

λの初期値は実験で調整する。後段では、品質の最低基準を制約として設定し、制約付き最適化に切り替えることも検討する。

## 実験計画

### 対象タスク

| タスク | データセット候補 | 評価指標 | 選定理由 |
|--------|-----------------|----------|----------|
| テキスト分類 | AG News subset | F1 | 正解判定が自動化しやすい |
| 情報抽出 | CoNLL-2003 subset | Exact Match | 構造化出力の評価が明確 |
| 推論 | ARC-Easy subset | 正答率 | 選択式で自動評価可能 |

各データセットから100〜200件を抽出し、訓練用（戦略の探索に使う）とテスト用（最終評価に使う）を分離する。

### 対象モデル

| モデル | サイズ | 量子化 | 想定用途 |
|--------|--------|--------|----------|
| Qwen2.5:1.5B | 1.5B | Q4 | 軽量・高速 |
| Phi-3:3.8B | 3.8B | Q8 | バランス型 |
| Gemma2:7B | 7B | Q4 | 高精度 |

16GB RAM環境で動作確認済みのモデルを選定する。実験開始時に利用可能な最新モデルに置き換える可能性がある。

### 比較手法

| 手法 | 説明 |
|------|------|
| Fixed-Best | 全タスクを最高精度のモデルで実行（精度の上限） |
| Fixed-Small | 全タスクを最小モデルで実行（速度の上限） |
| Rule-Based | 手動で設計したif-elseルール |
| Learned | タスク特徴量からモデルを予測する分類器 |
| EvoRoute | 進化的探索で改善したルーティング戦略 |

### 測定項目

- タスクごとの正答率
- 平均実行時間（推論のみ / ロード時間込み）
- ピークメモリ使用量
- モデル切り替え回数
- 探索にかかった総計算時間

## リスクと対策

| リスク | 対策 |
|--------|------|
| モデルの推論が遅く実験に時間がかかる | 結果をキャッシュし、同じ入力を再推論しない |
| 16GB RAMでモデルが載らない | Q4量子化を使用、同時に1モデルのみロード |
| 評価データが少なく統計的に不安定 | 複数回実行し分散を報告、bootstrap信頼区間を使用 |
| 進化的探索が収束しない | 世代数の上限を設定、探索空間を段階的に広げる |
