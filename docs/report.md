# EvoRoute 技術レポート

**ローカル LLM 間ルーティングにおける進化的探索の有効性の検証**

---

## 1. 要約

ローカル環境で動作する 3 つの LLM（Qwen2.5 1.5B / 3B / 7B、すべて Q4_K_M）に対し、
タスクごとに実行モデルを選択するルーターを 5 方式実装し、同一条件で比較した。
評価は精度だけでなく、**ローカル環境固有のコスト**——モデルのロード時間、常駐メモリ、
切り替え回数——を含む単一の目的関数 `J` で行った。

**結論は negative である。進化的探索（EvoRoute）は、最小モデルを常に使う方式を上回らなかった。**

ただしこれは「探索が失敗した」ことを意味しない。本レポートの主要な貢献は、
**なぜ上回らなかったのかを 3 層に分解して測定した**ことにある。

| 層 | 問い | 測定方法 |
|----|------|----------|
| Oracle | 完璧なルーターにどれだけの価値があるか | 動的計画法による厳密最適解 |
| 表現上限 | この特徴量で書ける規則は、どこまで到達し得るか | テスト分割上で直接探索（意図的なカンニング） |
| 到達値 | 訓練データから学習して実際にどこまで行けたか | 通常の train→test 評価 |

結果（warm ロード、test 分割、ベースライン `fixed-small` = 0.6147 を 0% とする）：

| 実行モード | 到達値 (EvoRoute) | 表現上限 | Oracle |
|-----------|------------------|----------|--------|
| online | **0.0%** | **3.4%** | 100% (J = 0.6591) |
| batch | **0.4%** | **33.5%** | 100% (J = 0.7191) |

- **online では、表現上限そのものがベースラインと統計的に区別できない**
  （+0.0015、95% CI [+0.0000, +0.0045]）。特徴量が足りないのではなく、
  **この条件ではルーティングという問題に解くべき中身がない**。
- **batch では上限の 33.5% が「表現可能だが到達できない」**。
  こちらは汎化の失敗であり、原因が異なる。

さらに、**最適なルーティング方針そのものが「振り分けない」に崩壊する条件**を特定した。
cold ロード × online 実行では、Oracle 自身がベースラインと区別できない
（+0.0014、95% CI [-0.0133, +0.0014]）。ロードコストが支配的な環境では、
どれほど賢いルーターにも奪える価値が残っていない。

## 2. 実験設定

### 2.1 モデル

提案書では量子化レベルを変数に含める計画だった（1.5B-Q4 / 3.8B-Q8 / 7B-Q4）。
予備測定の結果 **phi3:3.8b-Q8 は qwen2.5:7b-Q4 に対して遅延・メモリの両方で劣位**
だった。推論がメモリ帯域律速であるため、Q8 の 3.8B は Q4 の 7B よりファイル読み出し量が
大きくなる。支配される点を中段に置くと比較が無意味になるため、
**量子化を固定してパラメータ数だけを変数にした単調なフロンティア**を採用した。
量子化軸は本実験の範囲外であり、7 章に今後の課題として残す。

| tier | モデル | パラメータ | 量子化 | 常駐 (MB) | warm ロード (ms) | cold ロード (ms) |
|------|--------|-----------|--------|-----------|-----------------|-----------------|
| small | qwen2.5:1.5b-instruct | 1.5B | Q4_K_M | 1,057 | 542 | 1,649 |
| medium | qwen2.5:3b-instruct | 3.0B | Q4_K_M | 1,989 | 539 | 3,106 |
| large | qwen2.5:7b-instruct | 7.0B | Q4_K_M | 4,421 | 796 | 4,887 |

warm と cold はそれぞれ「Ollama からは追い出されたが OS ページキャッシュには残っている」
状態と、`sudo purge` でページキャッシュを破棄した初回接触の状態を指す。
中央値を取ると唯一の真の cold 測定値が捨てられてしまうため、別々に記録している。

### 2.2 データセット

各 100 件 × train/test、シード固定の排他分割。合計 600 タスク。

| タスク | データセット | 指標 |
|--------|-------------|------|
| 分類 | AG News (`fancyzhx/ag_news`) | ラベル一致 |
| 抽出 | CoNLL-2003 (`tomaarsen/conll2003`) | エンティティ F1 |
| 推論 | ARC-Easy (`allenai/ai2_arc`) | 選択肢一致 |

CoNLL-2003 については 2 点の前処理を行った。
(a) HuggingFace のスクリプト形式リポジトリが廃止されたため、ClassLabel 名を保持した
parquet 版を選定した。(b) 元データにはスポーツの順位表のような表形式の行が多数含まれ、
抽出タスクとして退化する（どのモデルも差がつかない）ため、散文のみを残すフィルタを入れた。

### 2.3 目的関数

提案書の定義：

```
J = Accuracy − λ₁·NormalizedLatency − λ₂·NormalizedMemory − λ₃·LoadSwitchPenalty
```

**この定義は実装中に破棄した。** 切り替えペナルティを独立に正規化すると、
`switch_ref = n × max_load` が ロード時間そのものに比例して動くため、
**ロードを 6 倍高価にしても最適解が変わらない**（検証時、切り替え回数はむしろ 68 → 74 に増加した）。
正規化が、測ろうとしていた当のコストを打ち消していた。

採用した定義は、推論時間とロード時間を**先に足してから一度だけ正規化**する：

```
J = Accuracy − w_time · (inference_ms + load_ms) / time_ref
              − w_mem  · (mean_resident_mb)      / mem_ref
```

- `w_time = 0.40`, `w_mem = 0.10`
- `time_ref` = 最も遅い単一モデルで全タスクを処理した場合の実時間（ロード 1 回を含む）
- 切り替えペナルティは独立項ではなく、**実測されたロード時間として時間項に入る**

この変更は回帰テストで固定している（`tests/test_objective.py::test_expensive_loads_suppress_switching`）。

### 2.4 実行モードとロード機構

ローカル実行には API ルーティング研究に存在しない自由度がある。

- **online**: タスクが到着順に処理される。tier が変わるたびにロードが発生する。
- **batch**: 全タスクを先に受け取り、tier ごとにまとめて実行する。各モデルは高々 1 回しかロードされない。

この 2 つはルーティング問題として別物である。online では切り替えが高価なので
「賢く振り分ける」価値が削られ、batch では切り替えがほぼ無料なので精度だけが効く。
両方を報告する。

### 2.5 測定の構造：応答行列

**全 (タスク × モデル) の組を 1 回だけ実測し、以降のすべての評価を辞書引きにした。**
1,800 回の推論（エラー 0 件）で行列を埋め、ルーター評価も進化的探索の適応度計算も
この行列を参照する。

これがなければ本実験は成立しない。GA の 1 回の実行は 60 世代 × 60 個体 = 3,600 回の
評価を行うが、素朴に実装すればそれだけで 3,600 × 300 タスク = 108 万回の推論になる。
行列化により **GA 1 実行あたり約 0.24 秒**（15,000 評価/秒）となり、
5 シード × 4 セル × 2 ルーターの全実行が 10 秒で終わる。

## 3. Week 1: 単一モデルのベースライン

test 分割上の精度：

| データセット | small | medium | large |
|-------------|-------|--------|-------|
| ag_news | 0.640 | 0.690 | 0.780 |
| arc_easy | 0.890 | 0.910 | 0.970 |
| conll2003 | 0.638 | 0.652 | 0.692 |
| **全体** | **0.723** | **0.751** | **0.814** |

タスクあたり平均推論時間は 183 / 389 / 877 ms。

**Oracle 精度（各タスクで最良のモデルを選べた場合）は 0.875**、
最良の単一モデル 0.814 に対し **+0.061**。
精度の観点では振り分ける余地が存在する。Week 1 の go/no-go はこれで GO とした。

一方で **ロード時間は推論時間の 4〜11 倍**である（cold の large で 4.9 秒、
タスク 1 件あたりの推論は 0.88 秒）。この比率が以降のすべての結果を決めている。

### 読み取り

1. **最も精度の高いルーターが、最も J を失う。** fixed-large は精度 0.814 で最高だが、
   J は 0.314 で最低。図 `01-objective-anatomy.png` がこれを 1 枚で示している。
2. **手動設計ルール（rule-based）はベースラインに大敗する**（0.3539 vs 0.6147）。
   63 回の切り替えで 41 秒を浪費し、精度 +0.042 では到底償えない。
3. **学習型も全敗。** learned-logreg は 141 回切り替え、+0.033 の精度のために
   87 秒のロードを買っている。`class_weight='balanced'` は有害だった（0.4559 vs 0.5965）。
4. **EvoRoute は online で fixed-small と完全に同一の方針に収束した**（300 件すべて small）。
   batch では 265/35/0 に分かれ、わずかに上回る。

## 5. 統計的検証

### 5.1 ブートストラップ信頼区間

`J(ルーター) − J(fixed-small)` の対応のあるブートストラップ（2,000 回）。

**移動ブロックブートストラップを用いた。** J はタスクの平均ではない——online では
連続するタスクの tier が変わるたびにロードを課金するため、統計量が**系列に依存する**。
タスクを独立に復元抽出すると、(a) 到着順が撹乱され、(b) 同一タスクの重複が隣接して
絶対に切り替えを起こさない位置に入る。どちらも再標本の J を実測値より上に押し上げ、
実際に**信頼区間が自身の点推定を含まなくなった**。連続ブロックを抽出することで、
切り替え回数を構成する局所構造を保存している（`tests/test_stats.py` で固定）。

**warm / online**

| ルーター | 差 | 95% CI | 判定 |
|---------|-----|--------|------|
| rule-based | −0.2608 | [−0.3585, −0.1941] | 劣る |
| learned-tree | −0.1588 | [−0.2166, −0.1219] | 劣る |
| **evoroute** | +0.0000 | [+0.0000, +0.0000] | **完全に同一の経路** |
| *evoroute-ceiling\** | +0.0015 | [+0.0000, +0.0045] | **区別できない** |
| oracle | +0.0444 | [+0.0262, +0.0577] | 優る |

**warm / batch**

| ルーター | 差 | 95% CI | 勝率 | 判定 |
|---------|-----|--------|------|------|
| utility-ridge | −0.0029 | [−0.0094, +0.0065] | 26% | 区別できない |
| **evoroute** | +0.0004 | [−0.0100, +0.0123] | **51%** | **区別できない（コイン投げ）** |
| *evoroute-ceiling\** | +0.0350 | [+0.0166, +0.0560] | 100% | 優る |
| oracle | +0.1045 | [+0.0771, +0.1335] | 100% | 優る |

**cold / online**

| ルーター | 差 | 95% CI | 判定 |
|---------|-----|--------|------|
| **evoroute** | +0.0000 | [+0.0000, +0.0000] | 完全に同一 |
| *evoroute-ceiling\** | +0.0000 | [+0.0000, +0.0000] | **完全に同一** |
| **oracle** | +0.0014 | [−0.0133, +0.0014] | **区別できない** |

最後の行が本実験で最も強い主張である。
**cold ロード × online 実行では、完璧なルーターですら「常に small」と統計的に区別できない。**
この条件下でルーティングは研究課題として空である。

### 5.2 到着順に対する感度

ここまでの online の結果には、報告されていない前提があった。
test 分割は `ORDER BY id` で読まれており、**データセットごとにタスクが連続して並んでいる**。
これはタスク種別に基づく規則にとって最も有利な並びであり、現実の到着ストリームではない。
ルーティングを固定したまま到着順をランダム化して再評価した（200 回、warm）：

| ルーター | id 順 J | 切替 | シャッフル J (mean±sd) | 切替 | 前提のコスト |
|---------|---------|------|----------------------|------|-------------|
| rule-based | 0.3539 | 63 | 0.2362 ± 0.0077 | 184 | **−0.1177** |
| learned-tree | 0.4559 | 75 | 0.3878 ± 0.0065 | 159 | −0.0681 |
| evoroute | 0.6147 | 1 | 0.6147 ± 0.0000 | 1 | ±0.0000 |
| oracle | 0.6591 | 54 | 0.6251 ± 0.0039 | 95 | −0.0340 |

cold ではさらに顕著で、rule-based は −0.5494、oracle は −0.0550 を失う。

2 点を意味する。
(a) **id 順の前提は、切り替えるルーターにのみ有利に働いていた**。
前提を外すと手動ルールと学習型はさらに悪化し、結論は変わらないどころか強まる。
(b) **Oracle は到着順に固有である**。ある順序に対して最適化された経路は、別の順序では
最適でない。これは到達可能な最適値についての主張ではなく、
事前計算されたルーティングの脆さについての主張である。

## 6. なぜ進化的探索は勝てなかったか

### 6.1 探索は正しく動いている

まず、探索自体の失敗ではないことを 3 方向から確認した。

1. **訓練適応度は確実に上昇している。** 図 `03-generation-curves.png` の batch セルでは
   train J が 0.652 → 0.663 に単調に上昇する一方、test J はベースライン上で平坦なままである。
   古典的な過学習であり、探索が動いていない兆候ではない。
2. **予算を増やしても改善しない。** 訓練データを 60 → 300 件に増やしたとき、
   最良値は 180 件以降ちょうど 0.614653（= fixed-small）で頭打ちになった。
   「データを増やせば天井に近づく」ではなく、
   **「データを増やすほど GA が確信を持って『常に small』に収束する」**。
3. **GA 固有ではない。** 同じカスケード特徴量を sklearn の学習器に渡しても、
   決定木分類器（深さ 2/3/4/6）、効用回帰木、リッジのいずれも `fixed-small` を超えない
   （`evoroute cascade` が再現する）。

   | 学習器 | J (test) | 常に small との差 |
   |--------|----------|------------------|
   | classifier tree depth=2 | 0.602537 | −0.012116 |
   | classifier tree depth=4 | 0.604234 | −0.010420 |
   | **utility tree depth=2** | **0.614653** | **±0.000000** |
   | utility tree depth=4 | 0.592204 | −0.022449 |
   | utility tree depth=6 | 0.575848 | −0.038805 |
   | utility ridge | 0.610727 | −0.003926 |

   最良は `utility tree depth=2` のちょうど 0.614653——「常に small」を学習しただけの完全同値である。
   木を深くするほど単調に悪化するのは典型的な過学習であり、
   **「探索が足りなかった」という説明は使えない。**

### 6.2 2 種類の壁

表現上限との比較が、条件によって壁の正体が違うことを示す。

```
online:   到達 0.0%  │  表現上限 3.4%  │  Oracle 100%
          └─ ほぼ全てが「特徴量の壁」。上限自体がベースラインと区別できない。

batch:    到達 0.4%  │  表現上限 33.5% │  Oracle 100%
          └─ 0.4→33.5% が「汎化の壁」、33.5→100% が「特徴量の壁」。
```

- **online**: 特徴量の問題ですらない。ロードコストが高いため、
  Oracle 自身が 245/41/14 と small に偏り、cold では 291/9/0 まで崩壊する。
  **奪える価値が存在しない。**
- **batch**: 上限の 33.5% は「この特徴量で書ける規則として存在する」が、
  300 件の訓練データからは GA にも sklearn にも見つけられない。**汎化の失敗。**

### 6.3 EvoRoute は「振り分けるな」を自力で発見した

目的 3（進化的探索が手動設計を上回るか）への直接の回答は以下である。

| | warm/online の J | 
|---|---|
| 手動設計 `rule-based` | 0.3539 |
| **進化的探索 `EvoRoute`** | **0.6147** |

**EvoRoute は手動設計のルールを +0.26 上回った。**
ただしその到達点は「常に small を使う」であり、これは人間が直感で書いたルールが
ベースラインより大幅に悪かったことの裏返しでもある。

重要なのは次の点である。
**正解を一切見ずに、GA は Oracle が cold/online で到達したのと同じ結論に独力で到達した。**
Oracle は正解スコアを見て 291/9/0 に崩壊する。GA は入力特徴量だけから
300/0/0 に収束する。探索機構としては正しく機能しており、
改善余地が実在しなかっただけである。

## 7. カスケードアーキテクチャの検証

入力だけから「大きいモデルが必要か」を予測できないなら、
**小さいモデルに一度解かせて、その出力を見てから判断する**ことはできる
（FrugalGPT のカスケードに相当する構成）。

小モデルの出力から 8 個の特徴量を追加した
（出力トークン数、行数、項目数、入出力比、散文性、反復、退化の検出など）。
コストは正直に計上している：小モデルの推論は**全タスクで必ず支払い**、
エスカレーションしたタスクは両方を支払う。小モデルは常駐とみなし、
エスカレーション先のスロットだけがロードを繰り返す。
エスカレーションしないカスケードは「常に small」と厳密に同一コストになるため、
両アーキテクチャはベースラインを共有する。

`evoroute cascade` の出力（warm ロード、test 分割、5 シード）：

| アーキテクチャ | モード | 常に small | 到達値 | 表現上限 | Oracle | 到達 % | 表現 % |
|---------------|--------|-----------|--------|---------|--------|-------|-------|
| 入力のみ | online | 0.6147 | 0.6147 | 0.6162 | 0.6591 | 0.0% | 3.4% |
| 入力のみ | batch | 0.6147 | 0.6151 | 0.6496 | 0.7191 | 0.4% | 33.5% |
| **カスケード** | online | 0.6147 | 0.6113 | **0.6267** | **0.6812** | −5.1% | **18.1%** |
| **カスケード** | batch | 0.6147 | 0.6080 | 0.6278 | 0.6970 | −8.0% | 15.9% |

（% は各アーキテクチャ自身の余地 `Oracle − 常に small` に対する割合）

読み取り：

1. **online では、カスケードが表現上限を 7 倍に広げた。**
   ベースラインを超える幅で見ると +0.0015 → +0.0105。
   「情報が足りない」という診断は正しかった。
2. **online では Oracle 自体も上がる**（0.6591 → 0.6812）。
   小モデルを常駐とみなせるため、切り替えが 1 スロット分で済み、
   ロードコストが下がるからである。カスケードは情報だけでなく**実行構造**も変えている。
3. **batch ではカスケードは有害。** 上限は 0.6496 → 0.6278 と 62% が失われ、
   Oracle も 0.7191 → 0.6970 に下がる。切り替えが既にほぼ無料な環境では、
   全タスクに小モデルの推論を課す「カスケード税」が情報の価値を上回る。
4. **広がった上限に、学習は届かなかった。** カスケードでの到達値は両モードとも負
   （−5.1%、−8.0%）で、ベースラインを下回る。
   広がったのは「表現できること」であって「学習できること」ではない。

アーキテクチャの良し悪しがロードコストの構造に依存するという、
提案書になかった知見である。**カスケードは online でのみ正当化される。**

## 8. 提案書の目的・成功基準への回答

### 目的

| # | 目的 | 結果 |
|---|------|------|
| 1 | ローカル LLM 間ルーティングを実装し固定モデル方式と比較 | 達成。5 方式 × 2 実行モード × 2 ロード機構 = 20 セルで比較 |
| 2 | ローカル固有コストをルーティング判断に組み込む | 達成。ロード時間・常駐メモリを実測して J に統合。**量子化軸は範囲外**（2.1 節） |
| 3 | 進化的探索が手動設計を上回るか検証 | 達成。**上回った**（0.6147 vs 0.3539）。ただし到達点はベースラインと同値 |

### 成功基準

- [x] 自作ルーターが動作し、タスクに応じてモデルを選択できる
- [x] 5 方式を同一条件で比較した実験結果がある
- [x] 進化的探索が他の方式と比べて改善するか、データで判断できる
- [x] ローカル固有のコストがルーティング判断に影響することを示せる
- [x] 実験を再実行して同じ傾向を確認できる（5 シード × ブートストラップ 2,000 回）

> 進化的探索がベースラインを上回らない場合でも、その原因を分析し、
> どの条件なら有効かの考察があれば成功とする。

**原因は 3 層に分解して測定した。有効な条件も特定した**（次節）。

### どの条件ならルーティングは有効か

本実験のデータから言えること：

| 条件 | ルーティングの価値 |
|------|------------------|
| ロードコスト ≫ 推論コスト（cold / online） | **なし。** Oracle ですらベースラインと区別できない |
| 切り替えが無料（batch、または全モデル常駐） | **あり。** Oracle で +0.105、表現上限で +0.035 |
| 入力のみの特徴量 | online では情報がほぼゼロ |
| 小モデル出力を見る（カスケード） | online の表現上限を 7 倍に。ただし 300 件では学習できず。batch では有害 |

実用的な含意として、**16GB クラスの単一マシンでモデルを入れ替えながら使う構成では、
ルーティングより「一番小さくて十分なモデルを選んで常駐させる」方が合理的である。**
ルーティングが意味を持つのは、複数モデルを同時に常駐できるメモリがある場合か、
バッチ処理でロードを償却できる場合に限られる。

---

## 9. 限界

1. **訓練データが 300 件しかない。** batch の表現上限 33.5% が到達不能である主因は
   ほぼ確実にこれである。ただし学習曲線（60→300 件）は天井に向かって上昇せず
   ベースラインに収束しており、単純な増量で埋まる保証はない。
2. **モデルが 3 つ、すべて同一ファミリ・同一量子化。** 単調なフロンティアを作るための
   選択だが、その結果「大きいモデルが得意な特殊なタスク種別」のような構造が存在しない。
   異なるファミリを混ぜれば、ルーティングに有利な相補性が生まれる可能性がある。
3. **単一マシン・単一実行。** 推論は temperature=0, seed=0 で決定的にしているが、
   実時間測定は 1 台の M シリーズ Mac での 1 回の測定である。
4. **タスク種別が 3 つのみで、データセット＝種別が 1 対 1 対応している。**
   タスク種別特徴量はデータセット識別子とほぼ同義になっている。
5. **Oracle は到着順に固有である**（5.2 節）。報告している Oracle 値は
   「その順序に対する最適値」であり、順序を変えれば別の経路が最適になる。

---

## 10. 今後の拡張

- **量子化軸の復活。** 同一モデルの Q4 / Q8 / FP16 を tier にすれば、
  支配されない点として量子化を変数に戻せる（2.1 節で断念した軸）。
- **複数モデル常駐を前提とした定式化。** メモリ上限を制約として明示し、
  「どの組を常駐させるか」と「どう振り分けるか」を同時に最適化する。
  本実験の batch モードはその極端な場合にあたる。
- **訓練データの拡大とカスケードの再評価。** online におけるカスケードの表現上限 18.1% は、
  到達可能な余地が実在することを示している。300 件という訓練データ量が主要な制約である可能性が高い。
- **到着順を含む評価。** 現実的なストリーム（混在・バースト）の下での
  オンラインルーティングは、本実験が触れていない別の問題である。

## 11. 再現手順

測定結果は `data/measurements.json.gz` に同梱しているため、**推論なしで全結果を再導出できる**。

```bash
uv sync
evoroute import-snapshot        # 応答行列 1,800 セルを復元
evoroute baseline && evoroute stats && evoroute cascade && evoroute figures
```

空の DB にスナップショットを読み込んで `baseline` を実行すると、
比較表の全行がビット一致することを確認している。
Docker（`docker build -t evoroute . && docker run --rm evoroute`）でも同じ。
**測定部分はコンテナ化していない**——macOS の Docker は Linux VM 上で動くため、
ロード時間とページキャッシュという測定対象そのものが歪むからである。

測定からやり直す場合：

```bash
uv sync
ollama serve &
ollama pull qwen2.5:1.5b-instruct-q4_K_M   # medium, large も同様

evoroute ingest                 # データセット取得・プロンプト生成・分割
evoroute profile --repeats 5 --purge   # ロード時間（cold は sudo が必要）
evoroute bench                  # 応答行列 1,800 セル（再開可能）
evoroute baseline               # 5 方式 × 2×2 の比較表
evoroute stats                  # ブートストラップ CI と到着順感度
evoroute cascade                # 入力のみ vs カスケード、sklearn 対照実験
evoroute figures                # 図 3 枚
pytest                          # 67 テスト
```

`evoroute bench` 以外はすべてキャッシュ済みの行列を読むだけで、数秒で終わる。
`bench` は中断しても `UNIQUE (task_id, tier, repeat_idx)` により完了済みのセルを
スキップして再開する。
